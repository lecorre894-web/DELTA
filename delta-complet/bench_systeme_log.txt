TEST 2 — L'AGENT SERT-IL À QUELQUE CHOSE ? (le seul juge qui compte)
══════════════════════════════════════════════════════════════════════════
  Trois régimes se succèdent dans la charge : balayage serré, accès
  dispersés, puis boucle sur peu de blocs. Aucun réglage immobile ne
  peut être bon sur les trois.

  régime                  secondes    taux   calculs  lectures
  FIXE G8 (le vrai optimum)      0.84   1.000         0     1,200
  FIXE G64 (mon ancien oracle)      5.03   1.000         0     1,200
  FIXE G128                   7.75   1.000         0     1,200
  AGENT                       5.45   1.000         0     1,200

  CORRECTION D'UNE ERREUR QUE J'AI PORTÉE TOUTE LA NUIT : mon
  « oracle » d'hier était G=64, parce que je n'avais testé que 64,
  256 et 1024. Le balayage complet (bench_reglage) montre que les
  granularités FINES gagnent largement. Mon oracle était donc faux,
  et tous les regrets que je t'ai annoncés étaient flattés.

  meilleur réglage FIXE (connu après coup, l'ORACLE) : 0.84 s
  pire réglage FIXE                                   : 7.75 s
  AGENT                                               : 5.45 s
  -> L'AGENT est entre le meilleur et le pire fixe : il évite le mauvais choix sans atteindre le meilleur.

  ET IL FAUT DIRE CE QUE CE BANC MESURE VRAIMENT : le taux de cache
  reste à 1,000 dans TOUS les régimes, parce que chaque lot est
  précalculé avant d'être lu. Le cache n'est donc jamais mis en
  difficulté, et la seule chose qui varie est le travail INUTILE fait
  d'avance quand le lot est trop gros. Le banc mesure donc « ne pas
  précalculer plus que nécessaire », ce qui est réel mais étroit.
